## 1 concept

1. Pairing is pairwise between two instances and done once by their administrators. Three instances form up to three independent pairings; there is no hub and no forwarding.
2. Each side keeps its own record of the other (`peers`, one row per `instance_id`) with two secrets: the inbound secret, which this instance issued and the peer signs its requests to us with, and the outbound secret, which the peer issued and we sign our requests to the peer with. Both are `EncryptedString` columns ([persistence.md section 2](persistence.md#2-models-and-column-types)), are never part of an API response, and are cleared when the pairing is revoked.
3. An instance is identified by its `instance_id` ([persistence.md section 5](persistence.md#5-public-ids-the-resolver-and-the-instance-id)), never by its address; its base URL is `DOMAIN`, the same value mail links and the passkey relying party use, and is announced in the handshake and in `/hello`.

## 2 where the code lives

1. Peering is instance-to-instance infrastructure, like webhooks, so it lives in Platform: the entities `domain/entities/peer.py`, the rules `domain/services/peering_rules.py` (codes, links, negotiation, signatures), the constants and the format and capability catalogue `domain/value_objects/peering.py`, the use cases in `application/use_cases/peering/`, the identity and message readers in `application/services/peering_identity.py`, the outbound port `ports/outbound/peer_client.py` with its httpx adapter `adapters/outbound/external/peering/httpx_peer_client.py`, and the routers `v1/peers_router.py` (admin) and `v1/peering_router.py` (surface).
2. Platform knows no recipe concept. The composition root registers the cookbook's formats and capabilities (`src/bootstrap/peering.py`), and the cookbook adds what happens on a revoke with `deps.register_peer_revoked_hook(factory)`, a factory taking the session and returning `async (Peer) -> None`, which runs inside the revoking transaction on either side. In the same way `deps.register_peer_changed_hook(factory)` adds what follows a change of a peer's switches or a renegotiation (`async (peer, changed field names, gained capabilities) -> None`, inside the transaction that saves it; Platform's own hook first makes the full comparison due when a capability was gained), and `deps.register_privacy_saved_hook(factory)` what follows a saved change of the privacy settings (`async (before, after) -> None`).
3. The transport ([section 11](#11-peer-channels) onwards) adds the entity `domain/entities/peer_channel.py`, the rules `domain/services/peer_channel_rules.py` (event types, retry schedule, timers, the sequence decision), the content ports `ports/outbound/peer_content.py`, the publish API `application/services/peer_channel.py`, the protocol messages `application/services/peering_messages.py`, the use cases `application/use_cases/peering/channel_sending.py`, `channel_receiving.py`, `channel_source.py` and `channel_jobs.py`, the repository `adapters/outbound/persistence/repositories/peer_channel_repository.py`, and the worker `src/bootstrap/peer_channel_worker.py`.

## 3 pairing

1. The administrator of instance A creates an invitation (`POST /admin/peers/invitations`, `write:settings`). The answer carries, once, the link `<A's base URL>/peering/accept?code=cuisine_pi_...`; only the code's SHA-256 is stored. The link works once and expires after 24 hours (`INVITATION_LIFETIME`). Open invitations are listed and can be revoked; invitations that expired more than 30 days ago are deleted when a new one is created.
2. The administrator passes the link on out of band. Opened in a browser, the link lands on the inviting instance's page `/peering/accept`, readable without signing in, which explains that the link belongs into the other instance's admin area (Administration, Peers, Accept an invitation) and shows it with a copy button; opening it there does not use the code. The administrator of instance B pastes it into B (`POST /admin/peers/accept {invitation_url}`), and B's server calls A's handshake ([section 4](#4-the-handshake)). Both admin areas then list the other instance.
3. A pairing with an instance that is paired and active is refused with 409 `PeerAlreadyPairedError`. After a revoke, either side may be invited again; the handshake then reuses the record of that instance with fresh secrets and versions, and keeps its switches. Every pairing, the first one and one after a revoke, runs the registered peer paired hooks inside the pairing transaction on both sides (`deps.register_peer_paired_hook`); the cookbook's hook sends the new peer every `peers` and `public` recipe at once. When the inviting side has no active pairing but the accepting side still has one (a revoke that never arrived), the accepting side takes over the new pairing.
4. An instance never pairs with itself (its own `instance_id`).

## 4 the handshake

1. `POST /api/peering/v1/handshake` is authenticated by the invitation code alone. The body is B's identity plus `code` and `secret`: `instance_id`, `name`, `base_url`, `app_version`, `protocol_versions` (supported, a list), `formats` (supported versions per format name), `capabilities`, and the secret A shall sign its requests to B with.
2. A checks, in this order: the code is known, unused and unexpired (else 401 `InvalidPeerInvitationError`, the same answer for all three); the identity is well formed, not A's own, and carries a valid secret; the versions overlap ([section 5](#5-versions-and-the-support-window)); no active pairing with that instance exists; B's base URL passes the https rule and the target guard. A refusal after a valid code leaves the code unused, so B can try again after an update.
3. A stores the peer, marks the code used in the same transaction (a conditional update, so two handshakes with one code cannot both succeed), and answers its own identity, `protocol_version` and `format_versions` (the negotiated values) and `secret`, the secret B shall sign its requests to A with.
4. B checks that the answer is well formed, that the chosen versions are ones B supports, and that A's announced base URL passes its own guard, and stores the peer. A refusal from A reaches B's administrator as 400 `PeerRefusedError` with A's message, shortened.
5. Readers ignore fields they do not know, so a newer release of the same protocol version may add fields.

## 5 versions and the support window

1. Three kinds of version are kept apart ([formats.md section 1](formats.md#1-formats-and-versions)): the app version is shown on the peer page and never decides anything; the format versions say how a payload is shaped; the protocol version says how the instances talk and is part of the path (`/api/peering/v1`).
2. A release supports the current and the previous protocol version (`SUPPORTED_PROTOCOL_VERSIONS`), and for peering the current and the previous version of each format (registered in `bootstrap/peering.py`; files import every version ever released, peering does not).
3. The handshake picks the highest common protocol version and, for every format both sides know, the highest common format version. Without a common protocol version, or without a common version of a required format (`cuisine-recipes`), the pairing is refused with 422 `PeeringVersionMismatchError` naming the versions of both sides. A format only one side knows, or an optional one without a common version, is left out of the negotiated set.
4. Capabilities (`equipment`, `extended_nutrients`, `seasons`, `variations` today) say what an instance can show of a peer's recipes. The peer page lists what a peer did not announce, so the administrator sees what is lost there.
5. Every peering request and every answer of the peering surface carries `Cuisine-Peering-Version`. A signed request without it, or with a version outside the support window, answers 422 `PeeringVersionMismatchError`; one with a version other than the negotiated one is accepted, and the authenticated request carries the version, so a caller can renegotiate.

## 6 authenticating peer requests

1. Every peering request but the handshake is signed the Standard Webhooks way, extended to bind the method and the path. Headers: `Cuisine-Peer` (the sender's `instance_id`), `webhook-id` (a fresh UUID per request), `webhook-timestamp` (Unix seconds) and `webhook-signature: v1,<base64 HMAC-SHA256>`. Several space-separated signatures are allowed, and one matching is enough.
2. The signed content is `"{webhook-id}.{webhook-timestamp}.{METHOD} {target}.{body}"`, where `target` is the path below the protocol root with its query string (`/hello`, `/changes?since=4`), so a reverse proxy in front of either side does not change what is signed, and the body is the raw bytes (empty for a GET). The key is the receiver's inbound secret as UTF-8 bytes. `peering_rules.sign_request` and `signature_matches` are the only implementations; every later signed peering request, event deliveries included, uses them.
3. The receiver (`AuthenticatePeer`) refuses with 401 `PeerAuthenticationError` when the headers are missing or malformed, the sender is unknown, the pairing is revoked, the timestamp is more than five minutes from its clock, no signature matches, or the `webhook-id` was seen before (the replay guard remembers it for eleven minutes, per peer). Every refusal is recorded with its reason and answers the same.

## 7 the peering surface

1. `/api/peering/v1` is a surface of its own: no person signs in there, the privacy acknowledgement does not apply, it is rate limited per address in its own bucket (`PEERING_REQUEST_LIMIT` per `PEERING_REQUEST_WINDOW_SECONDS`), and it answers 404 `PeeringDisabledError` while the feature switch is off. Maintenance mode refuses its writes like any other.
2. Routes: `POST /handshake` ([section 4](#4-the-handshake)); `GET /hello`, signed, which answers the identity, supported versions and capabilities of this instance and the versions negotiated with the caller, used as a health check and for renegotiation; `POST /revoke`, signed, the caller revoked the pairing ([section 8](#8-revoking-and-refreshing)); `POST /events`, `GET /changes?since=n` and `GET /items/{kind}/{id}`, signed, the peer channel ([sections 12 to 14](#12-events-and-sequence-numbers)).
3. The surface is left out of the OpenAPI snapshot (`include_in_schema=False`), since the web app never calls it; this file is its description, and the JSON Schema of every message is in `backend/formats/` ([formats.md section 8](formats.md#8-peering-protocol-messages)).
4. Every signed request that passes counts as contact: it sets the peer's `last_contact_at`, and when it names another protocol version than the negotiated one, the receiver queues a renegotiation (`ManagePeers.renegotiate`, which reads `/hello`), handled by the channel worker.

## 8 revoking and refreshing

1. `POST /admin/peers/{id}/revoke` (`write:settings`) marks the peer revoked, clears both secrets, deletes the peer's channel state, channel log and inbound queue, runs the revocation hooks and records the revoke in one transaction, then calls the peer's `/revoke`, signed with the secret it held. That call is best effort: when it fails, the answer says `peer_notified: false`, and the peer's next request is refused.
2. A signed `POST /revoke` from a peer marks it revoked the same way, with `revoked_by` `remote`. A `peer.revoked` event on `POST /events` means the same and is handled at once, not queued. The revoke is not sent as a queued channel event: the secret that would sign it is cleared in the revoking transaction, so the direct call is the only notice, and a peer that missed it learns of the revoke when its next request is refused.
3. `POST /admin/peers/{id}/refresh` reads the peer's `/hello` again and takes over its name, base URL (after the guard), app version, capabilities and the newly negotiated versions. When the peer cannot be reached, refuses, is another instance than the paired one, or no longer shares a version, the record stays as it was and the refresh answers the error. `ManagePeers.renegotiate(peer)` is the same without an administrator.
4. Secrets are not rotated in place; revoke and pair again for new secrets.

## 9 per-peer switches

1. Outgoing: `users_may_share` (on by default) governs everything the peer receives: while it is on, users may pick the peer as a share target, and the peer gets the recipes shared with it and every recipe whose effective visibility is `peers` or `public`; while it is off, it gets nothing. Incoming: `accept_incoming` (on by default; each recipe from the peer waits for an administrator), `mirror_visibility`, who sees accepted recipes: `instance` (everyone signed in, the default) or `group` with `mirror_group`, and `sync_all`, "sync all from this peer", which takes its recipes in at once with automatic catalogue decisions; a new pairing starts with it on, and pairing again after a revoke keeps the stored value like every other switch. A mirror has no owner on the receiving instance, so there is no household to scope it to, and household is not offered.
2. What the switches do to recipes is in [cookbook.md section 6f](cookbook.md#6f-sharing-with-paired-instances-and-mirrors): turning `users_may_share` off withdraws every recipe that went to the peer (and on again sends them), a new `mirror_visibility` applies to every mirror of the peer at once, and `sync_all` decides what arrives from now on; recipes that wait already are accepted with `POST /admin/peers/{id}/incoming-recipes/accept`.
3. `PUT /admin/peers/{id}/switches` takes all of them: `users_may_share`, `accept_incoming`, `mirror_visibility`, `mirror_group` and `sync_all`. An earlier switch that sent every public recipe is gone, since `public` includes `peers` and every public recipe goes to every peer that may receive.
3. `PUT /admin/peers/{id}/switches` (`write:settings`) saves them; `group` needs an existing group. A deleted group leaves the group choice without a group, which shows mirrors to nobody until the administrator picks another.

## 10 feature switch, outbound requests and the security log

1. The `peering` feature switch ([admin-area.md section 13](admin-area.md#13-feature-switches)) is on for a fresh instance, whose default visibility is `peers`, and independent of the webhooks switch. While it is off, every route of the peering surface and every `/admin/peers` route answers 404, the admin area hides the Peers tab, and a recipe set to `peers` reads as `instance` and goes to no peer. Switching it on or off publishes a new privacy statement version and runs the registered features saved hooks (`deps.register_features_saved_hook`), through which the cookbook withdraws or sends the `peers` recipes.
2. Every outbound peering request goes through `IPeerClient`: the webhook target guard checks the base URL and every address its host resolves to, with the private network switch of the notification settings ([admin-area.md section 5](admin-area.md#5-webhooks)); plain http is refused outside debug mode; the request goes to the checked address with the host name kept for the Host header and TLS; redirects are not followed; it times out after 10 seconds; an answer larger than 1 MB is dropped. Use cases check a peer's base URL with the same rules before storing it.
3. Security log entries ([auth.md section 7](auth.md#7-the-security-log)): `peer_invitation_created`, `peer_invitation_revoked`, `peer_paired` (with `role` `invited` or `accepted`, and the used invitation on the inviting side), `peer_pairing_refused` (a failure, with the reason `unknown_code`, `used_code`, `expired_code`, `version_mismatch`, `already_paired`, `invalid_identity` or `refused_by_peer`), `peer_changed` (switches or a refresh, with the changed field names), `peer_revoked` (with `by` `local` or `remote`) and `peer_auth_failed` (a failure, with the reason). Entries name the peer and invitation by public id and never carry a secret, a code or a value.
4. The log redaction blanks peer secrets (`cuisine_ps_`) and invitation codes (`cuisine_pi_`) ([admin-area.md section 12](admin-area.md#12-log-viewer)).

## 11 peer channels

1. A pairing gives each side one peer channel per peer, in both directions: as a source an instance publishes events about the items it shares with the peer, as a receiver it takes in the events the peer publishes. Each recipe or other item flows one way only, from its home to its copies.
2. A peer channel is a sibling of the webhook outbox ([admin-area.md section 5](admin-area.md#5-webhooks)), not a webhook subscription: it is written in the transaction of the change like a delivery, sent by a background worker and signed with the Standard Webhooks headers, but it has its own tables, signs with the peer secret ([section 6](#6-authenticating-peer-requests)), never gives up, and is not listed among the webhooks. The webhooks switch of the notification settings does not affect it; the `peering` feature switch does.
3. Tables: `peer_channels`, one row per peer keyed by the peer (the outgoing sequence counter `out_seq`, the sender's cursor `delivered_seq` with its retry state and last delivery result, the last processed incoming sequence `in_seq`, the timers, and the `send` and `receive` leases); `peer_channel_events`, the channel log, which holds the latest event per item and peer; `peer_inbox`, the events received from peers and waiting for the worker. All three are deleted with the peer and purged on a revoke. A channel whose row belongs to an earlier pairing (another `paired_at`) starts afresh on first use.

## 12 events and sequence numbers

1. Event types: `item.shared`, `item.updated` and `item.withdrawn` name an item by `kind` (such as `recipe`) and `id` with its `revision`; `peer.updated` carries the sender's app version, protocol versions, formats and capabilities; `peer.revoked` ends the pairing ([section 8](#8-revoking-and-refreshing)); `ping` proves contact once a day. The item events are content agnostic on purpose, so Platform never names a cookbook concept on the wire; the kind says what the item is.
2. Events are thin: `{type, seq, prev_seq, kind, id, revision}`, plus `peer` for `peer.updated`. The receiver fetches the content itself.
3. Every event gets the next number of the channel's sequence, which only grows. Publishing an event for an item replaces the earlier event of the same item in the channel log (control events replace the earlier one of their type), so only the latest state of an item is ever sent and the log doubles as the answer to "what changed since n". The sequence numbers in the log therefore have holes; each event names `prev_seq`, the sequence of the event before it in the sender's log, so the receiver can tell a hole from a missed event. A withdrawn item stays in the log as a tombstone until the pairing ends, so a receiver that was away for any length of time still learns of every withdrawal.
4. Item kinds and ids are limited to letters, digits and `._:-` (at most 64 and 128 characters), since they appear in signed request paths.

## 13 sending and retries

1. The channel worker sends the log entries above `delivered_seq` in sequence order, one `POST /events` each, at most 50 per peer and run. A 2xx answer moves `delivered_seq` on and counts as contact.
2. Any other answer, or a request that fails, stops the run for that peer. The next attempt follows after 1, 5, 30 and 120 minutes, then every hour for as long as it takes. A channel never fails for good and is never switched off; revoking the pairing is the only way to end it. The channel keeps the time, the HTTP status and a short category (`unreachable`, `invalid_target`, `refused`) of the last attempt, never the peer's text; peer deliveries are not written to the webhook delivery log.
3. One worker sends a channel at a time: the `send` lease is taken with a conditional update and runs out after five minutes, should the worker die.
4. Nothing is sent while the `peering` switch is off. Events are still written to the log meanwhile, so a channel switched on again sends what changed.

## 14 receiving, catching up and restores

1. `POST /events` checks the signature, timestamp and replay like every signed route, reads the event (a malformed one answers 422), stores it in `peer_inbox` and answers 202 at once. An unknown event type is stored and later skipped, so a newer peer's events do not stop the channel.
2. The worker processes a peer's queue in arrival order under the peer's `receive` lease. With `last` the last processed sequence (`in_seq`), an event whose `prev_seq <= last < seq` follows and is applied. One with `prev_seq > last` shows that events were missed (a gap), and one with `seq <= last` is a duplicate or comes from a source restored from a backup; both lead to a catch-up.
3. Applying an item event: `item.withdrawn` hands the id to the consumer's `withdraw`. `item.shared` and `item.updated` fetch `GET /items/{kind}/{id}` with `If-None-Match` set to the etag of the copy held here: 200 hands the bytes, media type and etag to the consumer's `apply`, 304 keeps the copy, and a 404 whose body says `"withdrawn": true` withdraws it. Any other answer, such as the plain 404 of a source whose feature switch is off, is a failure and withdraws nothing. Items are read up to 64 MB. A kind no consumer is registered for is skipped.
4. A catch-up asks `GET /changes?since=<last>`, which answers the latest state of every item whose sequence is above `since`, in sequence order (`item.shared` or `item.updated` with the revision, `item.withdrawn` as a tombstone), at most 500 per answer with `more` set while there are more, and the channel's highest sequence `max_seq`. The receiver applies each entry and moves `in_seq` on entry by entry, so a failure keeps the progress made, and finally sets `in_seq` to `max_seq`.
5. A `max_seq` below `last` means the source was restored from a backup: the receiver reconciles fully. It reads `/changes?since=0` to the end, applies every entry, and hands each consumer the full list of ids the source shares of its kind (`reconcile`), which withdraws every other item from that peer. `in_seq` then follows the source down to its `max_seq`, and the channel continues from there. A source restored and then busy enough to pass `last` again before the receiver checks is not detected this way; the daily comparison ([section 15](#15-timers)) repairs that case. A restored receiver simply catches up from its stored `in_seq`.
6. A failed fetch or catch-up leaves the event queued and retries it on the sender's schedule, never giving up, with the last category (`unreachable`, `refused`, `invalid_answer`, `consumer_failed`) on the channel. The timer's catch-up covers the same ground meanwhile, after which the queued event is a duplicate.

## 15 timers

1. The channel worker (`src/bootstrap/peer_channel_worker.py`) runs every 5 seconds on each backend worker's event loop. For every active peer it runs a catch-up every 15 minutes, a full comparison once a day and queues a `ping` once a day, whether or not events arrive. This is also how an instance that cannot receive events, for example behind NAT at home, stays current: there is no separate polling mode, only the catch-up on a timer.
2. The daily comparison works on both sides: as a source the instance asks every provider what it shares with the peer and publishes what the channel log is missing or has wrong (`RepairPeerChannel`); as a receiver it reconciles fully with `/changes?since=0` ([section 14](#14-receiving-catching-up-and-restores)), which also counts as a catch-up.
3. Each timer is claimed by moving its due time on with a conditional update, and the receiving work runs under the `receive` lease, so several workers never do the same work twice. A new channel catches up at once and compares and pings a day later.
4. `POST /admin/peers/{id}/sync` (`write:settings`) makes the catch-up and the next delivery attempt due now; the worker picks both up within seconds.
5. On startup the worker compares this instance's app version, protocol versions, formats and capabilities with what it announced last (`peering_announced` in the job state) and, when they differ, publishes `peer.updated` to every active peer. A receiver of `peer.updated` reads `/hello` again (`ManagePeers.renegotiate`).

## 16 the content ports and the publish API

1. The content is registered per item kind from the composition root with `deps.register_peer_content(kind, provider=factory, consumer=factory)`; each factory takes the session and returns the adapter. Both run on the session of the request or job that calls them; the transport commits, a provider or consumer never does.
2. The provider (`IPeerContentProvider`) is the source side: `shared_with(peer)` answers every item of its kind shared with the peer as `SharedItem(item_id, revision)`, for the daily repair; `fetch(peer, item_id)` answers `PeerItem(item_id, content, media_type, etag)`, or None when the item is not (or no longer) shared with the peer. The provider checks permission at fetch time, whatever the channel log says.
3. The consumer (`IPeerContentConsumer`) is the receiving side: `current_etag(peer, item_id)` for the conditional fetch, `apply(peer, item)`, `withdraw(peer, item_id)` and `reconcile(peer, shared_ids)`, which withdraws every item of its kind from the peer that is not listed.
4. A use case publishes inside its own transaction through `PeerChannel` (`Platform.peer_channel` in the dependency providers): `publish(peer_id, type, kind, item_id, revision)` for one peer, `publish_to(peer_ids, ...)` for every peer the item is shared with. `type` is `item.shared`, `item.updated` or `item.withdrawn`. Publishing to a revoked or unknown peer does nothing. `last_published(kind, item_id)` answers, per peer, the type and revision of the latest event about an item and `published_items(peer_id, kind)` the latest event per item for one peer, so a publisher can compare what a peer holds with what it should hold and publish only the difference. `/changes` answers from the channel log, so what a peer is told is exactly what was published for it; `/items` answers only what the provider says is shared with the calling peer.

## 17 the recipe kind

1. The cookbook registers the item kind `recipe` from `src/bootstrap/peering.py`: the provider is `PeerRecipeSharing` (`cookbook/application/services/peer_sharing.py`), the consumer `ReceivePeerRecipes` (`cookbook/application/use_cases/mirrors/receive_recipes.py`), together with the revoke, peer change, peer paired, privacy and features hooks. Item ids are recipe public ids at the source.
2. An item is a `.cui` file of one recipe (`application/vnd.cuisine.recipe+zip`, [formats.md](formats.md)) built for the fetching peer; its etag and revision are a hash over that payload and its images. Which recipes go to which peer, what the payload holds and which paths publish are in [cookbook.md section 6f](cookbook.md#6f-sharing-with-paired-instances-and-mirrors).
3. The consumer keeps a new recipe waiting for an administrator, applies updates whose catalogue entries all have a mapping, holds the others, removes the mirror on a withdrawal and keeps a rejected recipe rejected. For a peer with `sync_all` on it decides every entry without a mapping automatically and mirrors a new recipe or applies an update at once, never for a rejected one. `current_etag` answers the etag of what is waiting, else of the mirror, so an unchanged recipe is not fetched again.
4. A revoke removes every mirror, waiting recipe, catalogue mapping and dismissed suggestion of the peer on the receiving side. A gained capability makes the receiving side forget the etags of the peer's mirrors and waiting recipes, and the full comparison that Platform makes due at once fetches them again.
5. The catalogue data a peer sends is never written into the local catalogue by itself. Where it differs from a mapped local entry, it is offered to an administrator as a suggestion and accepted or dismissed per field ([cookbook.md section 4e](cookbook.md#4e-suggestions-from-paired-instances)).
