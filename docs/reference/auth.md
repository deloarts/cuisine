## 1 accounts

1. There is no sign-up and there are no usernames: every account signs in with its e-mail address, which is unique regardless of case (409 `DuplicateUserError`). The one exception is the system user, which also signs in as `system` (`SYSTEM_LOGIN` in `platform/const.py`); an address always holds an `@`, so the name never clashes with an ordinary account. A user may change it on the profile (`PATCH /users/me`), and the new address signs in at once. The system user is created from the `INIT__` settings at the first start (`bootstrap/seed.py`) and found by its `is_systemuser` flag; every other account is created by a holder of `write:users`. Every later start syncs it back to the `INIT__` values (full name, address `INIT__MAIL` and password), and it is reactivated. A password or address changed in the app therefore lasts only until the next start. An ordinary account holding the address blocks the sync, which is logged as an error.
2. The system user passes every permission check and cannot be deleted, deactivated or edited by anyone but itself, so the instance always keeps an administrator. Nobody can delete or deactivate their own account.
3. The system user is for administration only. Its two-factor authentication is mandatory (section 4), it cannot use passkeys (section 5), and its sessions end 15 minutes after sign-in (section 2). After signing in, the web app sends it to the admin area and shows a warning once per sign-in and tab, and the header counts down the rest of its session.
4. Deactivating an account, an administrator setting a new password and "sign out everywhere" raise the account's `token_version` and revoke its sessions, which ends every session token issued before. A user changing their own password (`POST /users/me/password`, which needs the current one) revokes every other session and every connected OAuth app (section 8 item 10) but keeps `token_version`, so the session that made the change stays signed in.
5. Two author name settings live on the user and only the user reads and changes them (`GET /users/me`, `PATCH /users/me`, the account's privacy section): `show_name_on_public_recipes` (off by default) decides whether visitors who are not signed in see the author of the user's public recipes, and `show_name_on_paired_instances` (on by default) whether the author's name travels with recipes shared to paired instances. Only the display name (item 6) ever leaves the instance, never the e-mail address. The public recipe pages read the first ([cookbook.md](cookbook.md) section 6e); peering will read the second.
6. A user may set a `nickname` (up to 64 characters, an empty string clears it) and choose `show_nickname` on their profile (`PATCH /users/me`); a holder of `write:users` may set both for anyone, when creating the account or later (`POST /users`, `PATCH /users/{id}`). The display name (`User.display_name`) is the nickname while `show_nickname` is on and a nickname is set, otherwise the full name. Every place that shows a person to someone else uses it: the person references of the cookbook (`PersonRef.display_name`), `UserSummaryResponse` and the people directory, MCP, `.cui` exports, peering payloads and public recipe pages. So the full name of someone who goes by a nickname is sent only to that user (`GET /users/me`) and to administrators (the user admin, the security log and the agent call log, which name the account by its full name).
7. An administrator may act on an account only when they hold every effective permission of it, its group permissions included (`assert_may_manage` in `domain/services/permission_rules.py`, 403 `UserOutranksActorError`). The rule covers changing the address, the password, the avatar (`PUT` and `DELETE /users/{id}/avatar`, stored as the user's own upload), the activity, the permissions or the groups of an account, resetting its two-factor authentication, signing it out everywhere and deleting it; the full name, the nickname and the language stay open to any holder of `write:users`. Taking rights away is therefore capped like granting them: nobody demotes an account that holds more than they do. The system user passes, and only the system user may act on the system user. Groups follow the same cap: removing a permission from a group needs that permission, and adding or removing a member or deleting the group needs every permission the group grants.
8. Groups are freely named permission bundles that stack, since there are no denials, and a group without permissions is only a sharing circle. The start that creates the system user also creates the default groups (`DEFAULT_GROUPS` and `ensure_default_groups` in `bootstrap/seed.py`): Cooks (`write:recipes`, `write:ingredients`), Kitchen helpers (`use:mcp`, `write:pat`), Curators (`manage:ingredients`, `write:resources`), Editors (`manage:recipes`), Administrators (`read:settings`, `write:settings`, `write:users`, `write:groups`, `read:security_log`, `manage:api_keys`) and the sharing circles Family and Friends. They have no members and are ordinary groups from then on, so an administrator may rename, change or delete them, and a deleted one does not return. Someone in no group reads what the visibility of each recipe allows and keeps their personal layer, meal plan and shopping lists, but writes no recipes.

## 2 sessions and CSRF

1. A successful login creates a `user_sessions` row and sets the `cuisine_session` cookie: httponly, `SameSite=Strict`, `Secure` unless `DEBUG`. The cookie holds a JWT carrying the user id, the token version and the session's public id, and no expiry of its own.
2. A session ends when its row is revoked, when it was idle longer than `session_timeout_minutes`, or when it is older than `session_max_lifetime_days`. The activity stamp is written at most once a minute.
3. A session of the system user instead ends 15 minutes after sign-in, whatever the user does (`SYSTEM_USER_SESSION_LIFETIME` in `domain/services/session_rules.py`). The limit is deliberately not a setting. Its cookie lives just as long, and its JWT carries the same end as `exp`, so the token dies even if a row check were bypassed.
4. `GET /users/me/sessions/current` returns the latest end of the requesting session (`expires_at`, null without an absolute lifetime) and the server's clock (`server_time`), so the web app can count down without trusting the browser's clock.
5. An unsafe request (POST, PUT, PATCH, DELETE) authenticated by the cookie must carry `X-Requested-With: cuisine` (403 `CsrfHeaderMissingError` without it). Forms and image tags cannot set it, and a script that could would have to run on an origin CORS allows, which is only `DOMAIN`.
6. A bearer header is accepted instead of the cookie, for tests and for the enrolment setup token.

## 3 the password step

1. `max_login_attempts` is at least 1 (422 below), so the lockout cannot be switched off. The throttle runs first, keyed on the normalised login (the e-mail address or `system`) and on the client IP (`login_throttle.py`, Redis-backed). A locked key answers 429 with `Retry-After` before the password is looked at.
2. An unknown address costs one bcrypt verification against a fixed hash, so it takes as long as a wrong password, and both answer the same 401. Both count as a failure.
3. An inactive account is reported only after its password was proven.
4. A correct password resets the name's counter but not the address's, so one valid account cannot reset a guessing run from that address.
5. The outcome is a session, a TOTP challenge (a five-minute token scoped `totp_pending`), or, when enforcement is on or the user is the system user and the user has no TOTP yet, a fifteen-minute setup token scoped `totp_setup` that only the enrolment endpoints accept.

## 4 two-factor authentication

1. TOTP follows RFC 6238 with 30-second steps; a code from the neighbouring step is accepted for clock drift.
2. A code is accepted once: the replay guard claims the user and code for 90 seconds, and a replay answers like a wrong code.
3. Failed codes count against a per-user key with the same limits as passwords.
4. Enrolment stores a new secret that only becomes active when a code confirms it. The secret is encrypted at rest. Enrolling from a session needs the current password in the body of `POST /users/me/totp/enroll` (403 `PasswordConfirmationError` when it is missing or wrong), so a stolen session cookie cannot put someone else's authenticator on the account. The setup token from the password step (section 3 item 5) enrols without it, since that step proved the password.
5. "Trust this device" stores the SHA-256 of a random secret, puts the secret into an httponly cookie scoped to `/api/v1/auth`, and skips the code (never the password) until it expires or is revoked. Disabling TOTP or an administrator resetting it revokes every trusted device.
6. With `enforce_totp` on, TOTP cannot be disabled; an administrator can still reset it for a user who lost their phone, who is then walked through enrolment at the next login.
7. The system user always needs TOTP, whatever `enforce_totp` says (`domain/services/login_rules.py`): its first sign-in walks it through enrolment, it cannot disable TOTP, "trust this device" is never offered to it, and no administrator can reset it in the app (403 `SystemUserProtectedError`). Only `admin reset-totp system` on the server clears it, and the next sign-in asks for a new setup.
8. Whoever holds `read:settings` or `write:settings`, directly or through a group, needs TOTP as well, whatever `enforce_totp` says (`login_rules.totp_mandatory`): a password sign-in without TOTP walks the account through enrolment, TOTP cannot be disabled while either permission is held (403 `TotpRequiredError`), and `totp_mandatory` on the user response says so. An account that gets such a permission while signed in, or that signed in with a passkey before enrolling, keeps its session, but every route behind either permission answers 403 `TotpSetupRequiredError` until it has enrolled; the admin area hides the settings tabs and links to the account page instead. Passkeys stay usable, and API keys and personal access tokens are not affected, since they never sign in with a password.

## 5 passkeys

1. Passkeys are WebAuthn credentials with user verification required, so a passkey replaces both the password and the code.
2. The relying party is the host name of `DOMAIN`; changing it orphans every registered passkey. Browsers allow WebAuthn only on https and on localhost.
3. The challenge travels in a five-minute signed token between the options and the verify request and is claimed once in the replay guard.
4. The WebAuthn user handle is the account's public id, never its sequential id or e-mail address; the authenticator lists the passkey under the e-mail address.
5. The system user cannot register passkeys (403 `SystemUserProtectedError`), and a passkey left over from before is refused at login, since a passkey would skip its mandatory code.
6. The sign-in page remembers up to five accounts that signed in on the device (`features/auth/utils/rememberedAccounts.ts`): the public id, what the form takes (the e-mail address, or `system`), the display name, a 96 px copy of the avatar and the credential id of the passkey the device used or registered. They live in the browser's localStorage only and nothing secret is among them. The page opens on the last account and offers its passkey, or its password when the device has none or the prompt is dismissed; "Forget on this device" removes an entry, removing a passkey on the account page drops its credential id, and deleting the account forgets it. After a password sign-in on a device with a built-in authenticator (Windows Hello, Touch ID, a phone's screen lock) the page offers to set up a passkey there, except to the system user, to an account that already has one on this device and to one that answered "Not now" on it; adding a passkey later clears that answer.

## 6 personal access tokens and API keys

1. Both are opaque random secrets with a prefix (`cuisine_pat_`, `cuisine_ak_`); only their SHA-256 is stored, and the plain value is shown once. Peering uses two more prefixes: an invitation code (`cuisine_pi_`) is stored as its SHA-256 like a token, while a peer secret (`cuisine_ps_`) signs requests and is therefore stored encrypted ([peering.md section 1](peering.md#1-concept)).
2. A PAT acts as its owner, narrowed to the token's permissions and, at use, to what the owner still holds. Creating one needs `write:pat`.
3. An API key acts as its own service account, which holds the key's permissions, never logs in and never appears among the people. Creating one needs `manage:api_keys`; using one needs `enable_api_key_auth` on (403 `ApiKeyAuthDisabledError` otherwise).
4. Neither can carry `write:settings`, `write:users`, `write:groups`, `manage:api_keys` or `write:pat`, and both are capped at the creator's permissions.
5. With `token_max_lifetime_days` above 0, every new token needs an expiry within it.

## 7 the security log

1. Logins (successful and refused, with the method and the reason), lockouts, logouts, password changes and confirmations, TOTP and passkey changes, revoked sessions and devices, account, group, token and settings changes, and OAuth registrations, approvals, refusals, revocations and reused OAuth tokens are recorded with the actor, the target account, the address and the user agent.
2. A record is written in the same transaction as the change it records.
3. Everybody reads the entries where they are the actor or the target; `read:security_log` reads all of them.
4. Peering is recorded too: invitations created and revoked, pairings (with the role), refused pairings (with the reason, including unknown, used and expired codes), changed and revoked pairings (with the side that revoked), and refused peer requests (with the reason). Entries a peer causes have no actor. The list and the reasons are in [peering.md section 10](peering.md#10-feature-switch-outbound-requests-and-the-security-log).

## 8 OAuth for hosted AI clients

Hosted AI clients (ChatGPT, claude.ai, Copilot Studio) cannot be given a token by hand, so Cuisine is an OAuth 2.1 authorization server for its own MCP surface, following the MCP authorization spec. The concept and the setup are in [MCP_INTEGRATION.md](../MCP_INTEGRATION.md); the protocol rules live in `platform/domain/services/oauth_rules.py`.

1. Discovery: `/.well-known/oauth-protected-resource/api/v1/mcp` (also at `/.well-known/oauth-protected-resource`, RFC 9728) names the resource `<DOMAIN>/api/v1/mcp` and Cuisine as its authorization server; `/.well-known/oauth-authorization-server` (RFC 8414) names the endpoints. Every refused MCP request carries `WWW-Authenticate: Bearer realm="cuisine", resource_metadata="…"`, with `error="invalid_token"` when a token was sent and `error="insufficient_scope"` for a missing permission. Both documents are built from `DOMAIN`, the issuer.
2. Clients register themselves at `POST /api/v1/oauth/register` (Dynamic Client Registration, RFC 7591), unauthenticated and rate limited per address (20 an hour). A redirect URI is https, or http on `localhost`, `127.0.0.1` or `::1`, without fragment, user info or wildcard; at most ten. The default `token_endpoint_auth_method` is `client_secret_basic`, as the RFC says; `client_secret_post` and `none` (public clients) are accepted. A confidential client's secret is shown once and stored as its SHA-256. A client nobody approved within 24 hours is pruned by the nightly retention purge. Client ID Metadata Documents are not supported.
3. The authorization endpoint is the web app's page `/oauth/authorize`. The session cookie is `SameSite=Strict`, so it never arrives with the cross-site navigation from the client; the page's own requests carry it. The page sends the query as it is to `POST /oauth/authorize/inspect` and the person's choice to `POST /oauth/authorize/decision`, both on the web surface with the session and the CSRF header, and both validate the whole request again.
4. An unknown client, a redirect URI the client did not register (exact match, except that a loopback URI may use any port, RFC 8252) or one outside the redirect host allowlist is shown on the page (`OAuthRedirectRejectedError`) and never redirected to. Any other broken request (a response type other than `code`, a missing or non-`S256` PKCE challenge, a `resource` other than the issuer or the MCP URL) is reported to the client through its redirect URI with `error`, `error_description`, `state` and `iss`.
5. Approving needs `use:mcp` and the `ai_agents` consent, which the page offers to give. The system user cannot approve (`SystemUserProtectedError`). The scopes are permission strings: `use:mcp`, always granted, `write:recipes` and `write:ingredients`; unknown scopes are ignored, and no known scope asks for all three. The page ticks what the client asked for that the person holds, and the person may untick the two write permissions.
6. An approval issues an authorization code that lives 60 seconds in Redis (`IAuthorizationCodeStore`) with the client, the redirect URI, the PKCE challenge, the permissions and the user's `token_version`. The token endpoint `POST /api/v1/oauth/token` (form-encoded, rate limited) redeems it once, with the PKCE verifier; a code redeemed a second time within ten minutes ends the grant it made. Its errors take the RFC shape `{"error", "error_description"}`, and every answer is `Cache-Control: no-store`.
7. A redeemed code becomes a grant, the connected app: user, client, permissions, redirect URI, `token_version` and a fixed expiry, the agent settings' `token_max_lifetime_days` from approval (or the general token cap when that is 0, or none when both are). A new approval of the same client by the same person replaces the earlier grant.
8. Access tokens (`cuisine_oat_`) last an hour, never past the grant. Refresh tokens (`cuisine_ort_`) last until the grant ends and are rotated on every use; presenting a rotated one again ends the grant and records `oauth_token_reused`. Both are opaque and stored as their SHA-256, so revocation takes effect on the next request. A refresh token works only for the client it was issued to.
9. The MCP surface accepts an OAuth access token like a PAT (`AuthenticateAgent`): the grant acts as its owner, narrowed to the grant's permissions and to what the owner still holds, with the same consent and privacy statement checks. The budgets and the call log key on the grant, so they survive the hourly change of the access token.
10. A grant ends when the person revokes it under Account, AI agents (`DELETE /users/me/connected-apps/{id}`), when the client revokes its refresh token (`POST /api/v1/oauth/revoke`, RFC 7009; revoking an access token ends only that token), when its expiry passes, when the user's `token_version` rises (deactivation, an administrator setting a new password, "sign out everywhere"), when the user changes their own password (the grants are revoked explicitly, recorded as `oauth_grant_revoked` with the reason `password_changed`), when the `ai_agents` consent is withdrawn, and when the user or the client is deleted.
11. The agent settings hold `oauth_enabled` and `oauth_redirect_hosts`. Off refuses registration, approval, the token endpoint and every OAuth access token (403 on MCP), and leaves PATs untouched. The allowlist holds bare host names, matched exactly without subdomains, empty meaning any host; it is checked at registration and at every approval, so removing a host blocks new approvals from clients that registered earlier, while grants already made keep working until they are revoked.
