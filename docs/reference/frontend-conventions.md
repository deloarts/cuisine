## 1 code style

1. TypeScript everywhere, `<script setup lang="ts">` in components, single quotes, no semicolons, two-space indent. There is no prettier config; match the style by hand.
2. oxlint, eslint (Vue strongly-recommended, TypeScript, accessibility, Vitest) and stylelint run in `npm run lint:check`. A floating promise is an error: `await` it, or hand it to `void` with its own `catch`.
3. Every form control has a label tied to it; an OpenVue Select takes `id` plus `aria-labelledby` pointing at its label. A file input carries `hidden` and is opened by a button through a template ref (`features/recipes/components/ImageUpload.vue`): a focusable input hidden with `visually-hidden` sits outside the scrolling main area, and focusing it scrolls the app shell out of place.

## 2 API calls and types

1. Call the web API through `webApi.get/post/put/patch/delete` from `core/api/webRequest.ts`. It takes the schema path (`'/users/{user_id}'`), checks path parameters, query and body against the generated types, and returns the response body.
   Only a feature's `api/*.ts` modules, `shared/api/*.ts` and the core stores call it; views, components and composables import those modules instead, so a spec mocks the feature's `api/` module rather than the request helper.
2. The login steps and the logout use `authApi`, the login page's instance info `publicApi` (`core/api/auth.ts`).
3. Wire types alias the generated schema: `export type UserResponse = Schemas['UserResponse']`. eslint refuses a hand-written interface named `*Response` or `*Request`.
4. After a backend change, `npm run generate:api-types` rewrites `core/api/generated/webSchema.ts` from `backend/openapi/openapi.json`; `npm run check:api-types` fails in CI when it is stale.
5. A 401 from the web API marks the session expired, and `App.vue` sends the user to the login page with a note.
6. Show a failed request with `useAppToast().error(err)`, which prefers the backend's `detail`.

## 3 styling and the look

1. The shell is the Glados one made calmer for a kitchen: a primary-coloured header with the brand in Lobster, a narrow icon sidebar that widens and groups its entries (everyday places and the kitchen catalogue, with only the admin icon at its foot, shown to anyone holding a permission of the admin area), the account and sign-out in the header's avatar menu, cards on a light surface, and the dark sign-in card over a warm glow, or over the background photo an administrator set in the General tab, which fades in from black once it has loaded. The default theme is the black `soul` palette in light mode.
2. Fonts ship with the app through `@fontsource` (imported in `main.ts`). Nunito (`--font-body`, `--font-head`) sets all text, including h3 to h6, amounts and tables. Lobster (`--font-display`, `--font-brand`) has a single weight and only sets the wordmark and the page titles: `h1` and `h2` use it at weight 400, so a heading that must stay plain text is an `h3` or uses `--font-head` explicitly. Never put Lobster on body text, numbers or form controls.
3. On a phone (below `$bp-sm`) the bottom nav (`app/layouts/AppBottomNav.vue`) is the main navigation with Home, Recipes, Meal plan, Shopping and More; More opens the sidebar as an overlay. Both read their entries from `app/navigation.ts`, which holds every entry with its permissions, so a new top-level page is added there once. A route with `meta.layout: 'fullscreen'` renders without header and navigation (cook mode). `meta.layout: 'guest'` renders the public recipe pages in `app/layouts/GuestLayout.vue` for visitors who are not signed in: the wordmark, a sign-in link and the legal links, nothing that needs a session, and the robots meta tag from `index_public_recipes` (`shared/composables/useRobotsMeta.ts`); a signed-in user opening such a page is sent to the full recipe pages. Public data comes through `publicApi`, never `webApi`, so a refusal never marks anybody signed out.
4. The admin area is one route, `/admin/:tab?`, with its tabs right under the header and the active tab in the URL. `features/admin-settings/adminTabs.ts` lists the tabs (Host, General, Users, Groups, Auth, AI agents, Catalogue, Legal, Storage and backup, Operations, Peers, Notifications) and the sections each stacks as cards, with the permissions every section needs and, when one component serves several sections, its props; a tab shows when one of its sections does, and a tab naming a `feature` only while that feature switch is on (Peers needs `peering`). A new admin setting goes into a section there, never into a page of its own.
5. Use OpenVue components, auto-imported by `unplugin-vue-components`. Change OpenVue's look through its tokens in `core/config/themePresets.ts`, through `--p-*` variables, or through the named classes in `assets/styles/_openvue.scss`. A component never styles OpenVue's internal `.p-*` classes; stylelint refuses it.
6. Use the shared classes of `main.scss` for the common patterns: `card`, `field`, `field-label`, `field-hint`, `hint`, `form-grid`, `panel-title`, `settings-tab`, `settings-fields`, `row-actions`, and `visually-hidden` for text only assistive technology reads.
7. Recipe text (description, tips, step texts) is a Markdown subset of bold, italic, bullet and numbered lists and line breaks ([cookbook.md section 1](cookbook.md#1-languages)). It is edited only with `shared/components/richText/RichTextEditor.vue` and shown only with `RichText.vue`; both take their rules from `richText/markdown.ts` (Tiptap's StarterKit cut down to the subset, and markdown-it with HTML disabled and only the subset's rules on). A new mark needs both sides changed there together. Step text also holds mentions, `@[Name](ingredient:<id>)`, `@[Name](recipe:<id>)` and `@[Name](equipment:<id>)` (`richText/mentions.ts`): only step editors pass `mentionable`, `@` offers the step's lines and equipment, the ingredient catalogue (showing a matched alias as "Tomate → Paradeiser"), the reader's recipes and the equipment catalogue, picking one the step lacks adds its line or equipment item, removing a line or item turns its chips into plain names, and `RichText` takes a `resolve` function that shows the current name, in cook mode the scaled amount, and links accessible sub-recipes. Titles, names and short notes stay plain `InputText`. The legal pages (imprint, privacy statement) are wider Markdown with headings and links, edited as plain text in the Legal tab and shown only with `shared/components/legal/LegalText.vue` (HTML disabled, links open in a new tab).
8. Spacing, font sizes and colours come from the tokens in `main.scss` (`--space-1` to `--space-6`, `--font-size-xs` to `--font-size-5xl`, `--p-*` colours); stylelint refuses literal values. A colour literal belongs in a custom property definition.
9. Styles are mobile-first. The base rules describe the phone; `@media (min-width: $bp-…)` queries add columns, space and side-by-side layouts as the screen grows. A `max-width` query is allowed only where a phone rule must override something a later rule cannot undo, such as OpenVue's inline dialog heights in `_openvue.scss`, and says so in a comment. Media queries take the breakpoints of `_breakpoints.scss`, which every style block sees without an import.
10. A component that appears in containers of different widths (the recipe card in the browse grid, the home rows and pickers) sizes itself with a container query (`container-type: inline-size` on its root, `@container (width < …)`) rather than a media query. Display type and spacing that should grow with the screen use `clamp()`.
11. Touch comes first: tap targets are at least 44 px (`2.75rem`), nothing depends on hover (hover effects sit inside `@media (hover: hover)`), and screens with fixed bars respect `env(safe-area-inset-*)`. Browse, the recipe page, cook mode, shopping and the meal plan are designed for the phone first; management tables stay usable on a phone but are tuned for the desktop.
12. Every page has the same content width. `AppLayout` puts each routed view into `.page-frame`, which spans the screen on a phone and is centred and capped at `--page-width` (`main.scss`) from there on. A view never sets a `max-width` or centring margin on its page container; an inner element may still limit itself, such as a form column or an image. Cook mode (`meta.layout: 'fullscreen'`) and the sign-in layout sit outside the frame, and dialogs keep their own widths. A bar that must span the whole main area, flush under the header and against the sidebar and the window edge (the admin tabs), teleports into `#page-bar`, which `AppLayout` renders before the frame and announces with `provide('pageBar', true)`; the bar sticks to the top and keeps the frame's padding below it.
13. Every data table is built on `shared/components/resource-view/ResourceTable.vue` with its state from `shared/composables/useResourceTable.ts`, never on a bare DataTable. `useResourceTable(tableKey, filterSpec, reload?)` keeps the filters in the URL (`useUrlFilters`), the rows per page per table on the device (`useTableRows`) and the current page, and goes back to the first page and calls `reload` when a filter or the page size changes. The component has no toolbar around it: a page puts its create action in its `PageHeader` (or a section its own heading row), and the `header` slot renders inside the table's card above the grid, for tabs or a notice. It brings one filter per column in the header row (`filter-display="row"`, a `filter-<field>` slot for each column marked `filter`), a row number column whose filter cell holds the "clear filters" button while a filter is active, the paginator and an empty state. Cells come from `body-<field>` slots and never wrap (a column marked `wrap` may), so a wide table scrolls sideways in its card. Row actions are a context menu built by the `menu` prop (a right click, and a trailing button on a phone), never a column of buttons; with `clickable` a row click emits `rowClick`, usually to open the row's edit dialog. A browser-side table sorts by every column, by default by the first one ascending (`sortField` names another property or a function of the row when the cell shows a label, `default-sort` picks the column or null keeps the given order); a lazy table sorts only the columns marked `sortable` and reads `sortField` and `sortOrder` from its state when it loads. `reorderable` replaces sorting and paging with a drag handle and emits `reorder` with the rows in their new order. A table with `total` is lazy and its owner loads each page from the server; without it the owner passes the filtered rows (`shared/composables/tableText.ts` matches text without case and diacritics) and the table pages them. With `fill` (the default) a page that is a `.table-page` (`main.scss`) gives the table the rest of the height from `$bp-sm` up, so its header sticks and its body scrolls; a table inside a stacked section (admin tabs, account tabs, dialogs) passes `:fill="false"` and scrolls inside a capped height. On a phone the table shows only its `phone` columns (the first one by default) with the `phone` slot under the lead cell, and the filters stack in a panel that a button at the top of the card opens. Two tables on one page take different filter keys; a page with tabs puts the tab in the route and drops the query on a tab switch. Numeric ranges use `shared/components/table-filters/NumberRangeFilter.vue`, ported from Glados; `features/ingredients/views/IngredientsView.vue` is the reference for a server-side table and `features/resources/components/UnitsTab.vue` for a browser-side one. A cell without a value stays empty, with no dash or other placeholder. A table of catalogue items shows no status column: a draft carries a warn tag beside its name, and for the people who may activate drafts the matching ones are passed as `pinned`, frozen rows above the sorted list with a pin instead of a number, and left out of `value`.
14. A page or section that loads its content shows OpenVue's `Skeleton` in the shape of that content until it arrives: the same grid, card sizes and line counts, so it fills in without moving. The shapes sit in `shared/components/skeleton/SkeletonRegion.vue`, which announces the wait once to assistive technology (`silent` for every further placeholder on the same page) and takes the class of the content it stands in for; `SkeletonLines`, `ListItemSkeleton`, `FieldSkeleton` and `DialogBodySkeleton` next to it and `shared/components/recipes/RecipeCardSkeleton.vue` cover the common shapes. A view keeps the data it shows during a reload of the same content, and `ResourceTable` shows skeleton rows only while it has none. A spinner is left for an action in place: a button's own `loading` while it saves, the grid's overlay over rows already shown, an upload, a preview refreshing beside its editor, or a redirect whose target is not known yet.
15. Dark mode is the `.p-dark` class on `<html>`, which OpenVue's variables follow. Never `@media (prefers-color-scheme: dark)` in a component.
16. Each user picks an OpenVue preset, an accent colour and a surface on the account page; the names must match `core/config/colorPalettes.ts` and the backend's `domain/value_objects/theme.py`.
17. No Tailwind or other utility-CSS framework.
18. Printing is styled with `@media print` in the scoped CSS of the page and its layout. The layouts hide their own chrome on paper (`AppLayout` the header, sidebar, bottom nav, banners and legal links; `GuestLayout` its header and footer), `main.scss` lets the document grow over several sheets, and `layoutStore` drops `.p-dark` between `beforeprint` and `afterprint`, so paper is always dark ink on white. Only the signed-in recipe page (`RecipeView.vue`) prints its content: the recipe as it is on screen, with the chosen servings, content language and variation, and a QR code (`RecipePrintQr.vue`, drawn locally with `qrcode`) for `<origin>/r/<public id>`. Its controls, the variation switcher, warnings, the reader's own layer and other cooks' history carry the class `screen-only`, and text meant only for paper carries `print-only`. Public pages never print a recipe: the public recipe page prints a note to sign in instead.
19. `/r/:publicId` (`features/resolve/`) opens any link by public id for a signed-in reader: it asks `GET /resolve/{public_id}` and replaces itself with the route it answers, and a 404 shows that the link leads nowhere. QR codes, mails and agents link through it rather than to a page path.
20. Pickers show enough of each item to choose the right one, through the shared rows and selects rather than a bare `option-label`. A unit is picked with `shared/cookbook/UnitSelect.vue`, which groups the units by kind, shows each one's abbreviation, name and worth in grams or millilitres, and shows only the abbreviation once chosen; given the line's ingredient it says what one unit of it weighs and mutes a unit it cannot be weighed in, by the rule of `shared/cookbook/units.ts`, which follows the backend's `to_grams`. An ingredient suggestion renders `IngredientOption.vue`, whose `meta` names the details that picker needs (category for shopping, family and allergens for a food restriction, owner and language for merging); a recipe renders `RecipeOption.vue` with its cover, time, difficulty and author; an equipment item `EquipmentOption.vue` with its icon and the alias the search matched. People are picked with `shared/cookbook/UserPicker.vue` (several, as chips) or `shared/components/PersonSelect.vue` (one), both showing the avatar through `PersonOption.vue`; the directory (`GET /users/directory`) carries `avatar_id` for that. Pickers that add an item to a list, such as a step's ingredients and equipment, are AutoCompletes with a `dropdown` button: typing searches at once, picking adds the item and empties the input. A step's ingredient picker first offers, under the heading "From the ingredient list", the declared lines the steps do not use up yet (`listSuggestions` in `features/recipes/utils/ingredientSummary.ts`), filtered by what is typed: an unused line is added with its declared amount and unit, a partly used one with the amount still missing in its declared unit, and the catalogue results below do not repeat them.
21. Cuisine installs as an app on a phone. `index.html` links the manifest the backend writes from the general settings ([admin-area.md section 4](admin-area.md#4-general-settings)) and the Apple touch icon. `vite-plugin-pwa` builds a service worker (`vite.config.ts`) that precaches the app shell (scripts, styles, the Latin font subsets, icons and `index.html`) and answers navigations with that shell, except for the paths the backend or nginx answer themselves. Requests below `/api` always go to the network, so the worker never serves a stale recipe or session. A new release activates on the next start of the app. The icons in `public/icons/` are rendered from `public/favicon.svg` by `scripts/generate-pwa-icons.sh`; run it again after changing the favicon. The service worker runs only in a build, never under `npm run dev`, and installing needs HTTPS or `localhost`.
22. Every card is `shared/components/ContentCard.vue` (`as` renders it as a `section`, `form`, `li` or `ul`), never a bare element with the `card` class; the class itself stays for ResourceTable's card and the skeleton stand-ins. Its inner padding is the shared `--card-padding` (`assets/styles/main.scss`, 1rem on a phone and 1.5rem from the small breakpoint up), so text keeps the same distance from the border everywhere. A card does not set its own padding, except `padding: 0` for one whose rows run to the border (a list of items) and the dense grids (the cook calendar, the kitchen lists, the editor's tab bar).

## 4 i18n

1. The core strings (common words, navigation, sign-in, account, administration, permission labels) live in `core/i18n/locales/en-GB.ts` and `de-AT.ts`, nested by area.
2. A feature keeps its own strings in `features/<feature>/locales/en-GB.ts` and `de-AT.ts`. Each file default-exports one object whose top-level keys are the feature's namespaces, usually one named after the feature in camelCase (`mealPlan` for `meal-plan`). `core/i18n/index.ts` loads every module through `import.meta.glob` and merges it on the top-level keys (`core/i18n/messages.ts`), so adding a feature never edits a shared file. A namespace belongs to one source only: a module never adds keys to `common`, `nav` or another feature's namespace; a string several features need goes into the core file.
3. Every key exists in both languages, in the core file and every module alike. `npm run check:i18n` fails on a missing key, a module with only one language, a namespace that two sources define, and a permission without a label.
4. German copy uses the informal "Du", consistently: "Melde dich an", "deine Sitzung".
5. English is the fallback. Before sign-in the locale is the instance's default language (`default_language` of the public info, applied by `publicInfoStore` while nobody is signed in); after sign-in it is the user's own language.
5a. OpenVue's own texts (empty lists, result counts read to screen readers, the dialogs' close button) follow the UI language: `core/i18n/openvueLocale.ts` holds them in both languages and `main.ts` swaps them whenever the locale changes. A new OpenVue component whose texts show up in English gets its keys added there.
6. Use named interpolation (`{name}`), never string concatenation of translated parts.

## 5 stores and session

1. `currentUserStore` holds the signed-in user. The router's guard calls `refresh()` once on the first navigation; a 401 then simply means nobody is signed in.
2. The session cookie is invisible to the app. "Signed in" means `/users/me` answered.
3. `layoutStore` applies the user's theme from their profile and the OS dark-mode preference before sign-in.
4. Browser storage goes through `core/utils/safeStorage.ts`, which never throws, so a private window or blocked site data only means nothing is kept. It holds device conveniences (the sidebar width, rows per page, a dismissed banner) and the editors' unsaved drafts, never a session token, a password or data the user has not typed or chosen themselves.
5. An editor whose work would be lost by leaving the page keeps its unsaved form on the device with `core/utils/editorDrafts.ts`, keyed by user and editor scope (`recipe:new`, `recipe:<id>`, `variation:<recipe id>:<variation id or new>`), so people sharing a device and different records never mix. `features/recipes/composables/useEditorDraft.ts` stores the form debounced and when the page is hidden, keeps only a form that differs from the server's version, restores a stored draft on the next visit with a notice and a discard button, and says so when the record changed on the server after the draft was stored (its `changed` timestamp). A draft holds the form's plain values and the ids of files already uploaded, never a file itself. It is dropped after a successful save and after a cancel, which asks first while there are unsaved changes. Signing out (`currentUserStore.clear()`: logging out, declining the privacy statement, deleting the account) removes that user's drafts from the device; an expired session keeps them, so the work is still there after signing in again.
